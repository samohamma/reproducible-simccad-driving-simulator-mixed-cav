# Reproducible Mixed-CAV Driving-Simulator Experiment Framework

This repository contains the Webots/SimCCAD implementation used for the revised paper on reproducible driving-simulator experiment design for mixed human-driven and connected/automated vehicle (CAV) research.

The project demonstrates a **design-to-implementation-to-feasibility-checking workflow**:

1. define experiment parameters in Python;
2. generate Webots `.wbt` worlds programmatically;
3. run candidate scenario variants in Webots;
4. record simulation-speed feasibility metrics;
5. generate figures for the paper.

The current benchmark extension varies the number of surrounding CAVs while keeping the road geometry, controller structure, and scenario logic fixed. The purpose is not to identify a universal optimum, but to demonstrate how a reproducible framework can evaluate candidate parameter settings under a specified hardware/software setup.

## Python Dependencies

Install the Python packages listed in:

```bash
requirements.txt
```

For example:

```bash
python -m pip install -r requirements.txt
```

Main external packages:

- `numpy` — controller calculations and figure processing;
- `pandas` — benchmark-result processing;
- `matplotlib` — publication figure generation;
- `openpyxl` — optional Excel input support for figure generation;
- `pygame`, `playsound`, `PyOpenAL` — participant/driver controller audio/display support;
- `pywin32` — Windows file-locking support used by controller utilities.

Webots provides the controller runtime modules such as `controller` and `vehicle`; these are not installed through `pip`.

## Main Commands

Run commands from the project root.

### Generate the baseline experiment world

```bash
python main.py
```

This writes:

```text
worlds/ExperimentDesign.wbt
```

### Generate benchmark worlds only

```bash
python main.py --benchmark-generate-only
```

This writes:

```text
worlds/bench_cavs10.wbt
worlds/bench_cavs11.wbt
...
worlds/bench_cavs39.wbt
```

### Generate and benchmark all scenarios

```bash
python main.py --benchmark --mode run
```

This performs the full workflow:

1. generate `ExperimentDesign.wbt`;
2. generate benchmark worlds `bench_cavs10` to `bench_cavs39`;
3. run each benchmark world in Webots `run` mode, corresponding to Webots Ctrl+3;
4. record real-time-factor metrics;
5. save consolidated outputs in `Extracted data/performance/`.

### Safe one-scenario test

```bash
python main.py --benchmark --mode run --max-scenarios 1 --max-worlds 1
```

### Generate figures from existing benchmark output

```bash
python scripts/generate_rtf_figures.py
```

This reads:

```text
Extracted data/performance/all_scenarios_rtf_timeseries.csv
```

and writes figures to:

```text
Extracted data/performance/rtf_figures/
```

## Benchmark Protocol

The default benchmark varies only one design variable:

```text
total number of surrounding CAVs
```

The current default sweep is:

```text
10, 11, 12, ..., 39 surrounding CAVs
```

All other core experiment-design variables are held fixed in `BASELINE_EXPERIMENT` inside `main.py`.

The benchmark uses:

```text
mode = run
```

which corresponds to Webots Ctrl+3. Do not use `realtime`/Ctrl+2 for the benchmark unless explicitly testing a different condition.

The default measurement settings are:

| Setting | Value |
|---|---|
| Warm-up excluded | first 5 simulation seconds |
| Maximum measurement window | 30 simulation seconds after warm-up |
| Basic timestep | 50 ms in the current worlds |
| Adaptive stop | enabled by default |
| Adaptive stop condition | stop before the ego vehicle reaches the on-ramp traffic-light boundary |

The adaptive stop prevents the benchmark from continuing into an unintended downstream/crash-prone phase for low-density/high-speed scenarios.

## Real-Time-Factor Metric

The main simulation-speed metric is:

```text
real_time_factor = measurement_sim_time / measurement_wall_time
```

Interpretation:

| Value | Meaning |
|---:|---|
| `1.0` | simulation progresses at real time |
| `< 1.0` | simulation is slower than real time |
| `> 1.0` | simulation is faster than real time |

The per-step diagnostic metric is:

```text
step_real_time_factor = sim_dt / wall_dt
```

This value is intentionally retained for diagnosis, but it is noisy and should not be used as the primary comparison metric.

## Controller Overview

The automated surrounding vehicles use longitudinal car-following logic based on the Full Velocity Difference Model (FVDM) and lane-centred lateral control using a PID-style controller. The controller suite also includes ego-vehicle automation before takeover, a racing-wheel takeover controller, a broken-vehicle/takeover trigger controller, stop-and-go vehicles, and the benchmark profiler.

Traffic-light nodes are used not only as visible traffic infrastructure but also as synchronisation and trigger references for scenario phases. Their DEF names intentionally follow the legacy racing-wheel-compatible naming convention:

```text
TL_onrmp0, TL_img_StnGo0, TL_img_takeOver0, TL_offrmp0
TL_onrmp1, TL_img_StnGo1, TL_img_takeOver1, TL_offrmp1
...
```

## Reproducibility Notes

- The benchmark worlds and metadata are generated from `main.py`.
- The benchmark runner temporarily injects the performance profiler into the world being tested and restores the world afterward.
- Benchmark outputs currently retained in this repository are part of the reproducible record for the revised manuscript.
- Runtime outputs may change if the machine, Webots version, graphics load, background processes, or controller code changes.
- Hidden `.wbproj` files are Webots project-view files and are not the core reproducibility artefact; the `.wbt`, controller scripts, metadata JSON, and benchmark CSV files are more important.

